Important corrections I learned
Constructor should be public if called from Main or outside the class.
Static methods cannot access instance fields directly.
Use instance methods like Display() for object data.
If using private fields, use properties or methods to access them.
Auto-property public int Age { get; set; } creates hidden storage.
Do not create both private int age and public int Age { get; set; } unless the property uses the field.
Avoid property recursion like get { return Name; } set { Name = value; }.
Correct full property uses a private field:
csharp
private string name;
public string Name
{
    get { return name; }
    set { name = value; }
}
Use protected for parent class data if child classes need access.
Abstract method has no body and must be overridden by child classes.
Virtual method has a body and may be overridden.
base(name, age) calls the parent constructor.
Interface methods are implemented without override.
Use override only for abstract/virtual methods from a parent class.
In C#, a class can inherit from only one class but can implement many interfaces.
When combining inheritance and interfaces, base class comes first:
csharp
public class Teacher : Person, IDisplayable, IPayable
For method overriding, use virtual in parent and override in child.
For method hiding, use new, but it is not true runtime polymorphism.
Use int.TryParse instead of Convert.ToInt32 when validating console input.
Use string.IsNullOrWhiteSpace to validate text input manually.
In Web API, services should return data/status/results, controllers should return HTTP responses.
Use [HttpPut("{id:int}")] not [HttpPut("{id : int}")].
Prefer [FromBody] for request body.
Prefer clear variable names like updated, deleted, owner, customer, booking.
Return BadRequest for invalid route IDs.
Return NotFound when service cannot find data.
Return CreatedAtAction for POST create endpoints.
Use ActionResult<T> in controllers.
Interface implementation does not use override.
With [ApiController], Data Annotation validation can automatically return 400 Bad Request.
Route values like id still need manual validation.
Data Annotations can validate format/range, but cannot check if related data exists.
Business validation like “owner exists”, “car is available”, “customer exists” stays in controller/service logic.
Car availability should not be manually updated through normal car update anymore.
Car availability should change through booking actions:
Create booking -> IsAvailable = false
Cancel booking -> IsAvailable = true
Complete booking -> IsAvailable = true
AddSingleton is okay only for current in-memory lists.
EF Core DbContext uses scoped lifetime.
Services using AppDbContext should be registered with AddScoped.
Do not inject scoped service into singleton service.
Once a service is registered as interface mapping, inject the interface, not the concrete class:
csharp
builder.Services.AddScoped<IOwnerService, OwnerService>();
public OwnersController(IOwnerService ownerService)
Include() is used to load related data.
ThenInclude() is used to load related data of related data.
Response DTOs help avoid returning full EF entities directly.
Response DTOs make API responses cleaner and safer for frontend use.
For fast delivery, focus on one vertical slice end-to-end instead of building many incomplete roles/features.

In Version 1, the owner will manually enter trip details.
Daily/monthly trip reports and earnings are now a top priority for release.

app.UseAuthorization();
JWT token claims can be used to identify the logged-in owner.
Owner-specific endpoints should use token-based identity instead of requiring owner id manually in route when possible.
Controller access control and service logic are different concerns.

Current real project
Project name: CarBookingAPI

Important clarification
Although project name is CarBookingAPI, the long-term idea is a trip booking platform.

However, for fast delivery, the current product direction is a vertical slice MVP focused on owner operations first.

Version 1 product direction
Only Owner role is active.
Owner registers/login.
Owner manages own cars.
Owner manually enters trip details.
Owner views trip history and earnings reports.
Customer role is postponed for later versions.
Driver role is postponed for later versions.
Admin role is postponed for later versions.
Main entities currently in project
Owner
Car
Customer
TripBooking
Important temporary business decision
Customer entity may still exist in the project/database, but Version 1 does not depend on customer login flow.

In Version 1, trip details are entered manually by the owner after login.

This means the system behaves more like an owner trip-record and earnings management API in the first release.

Later versions can evolve this into a full customer booking platform.

Relationship idea
Owner owns/registers cars.
Car has OwnerId.
Customer does not connect directly to Car.
Customer connects to Car through TripBooking.
TripBooking has CustomerId and CarId.
For Version 1, owner-based reporting is a key use case.
